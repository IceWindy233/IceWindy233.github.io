一些AiAgent开发随手笔记

发表于2026-07-22|更新于2026-09-08|大模型应用笔记

RAG系统如何处理Word、PDF

解析

  • Docling / Marker：文档解析器，转换为Markdown文件

  • 云解析方式处理：Llama Parse等闭源方案

  • 处理表格类：先转换为HTML或JSON

  • 混合图文复杂文档、解析效果差：采用ColPali架构

    • 离线建库：

      1. 将文档转换为图片
      2. 通过VLM模型提取视觉特征向量
      3. 存入向量数据库

    • 在线查询：

      1. 用户输入文本查询
      2. 输入到同一个 VLM 的语言模型部分，生成一系列文本特征向量
      3. 匹配向量数据库内相似度

  • 智能解析路由：使用一个视觉小模型进行文档分类，一般文档采用Docling/Marker等方式，复杂文档采用ColPali架构

切片

  • 采用结构感知切片，依照解析出来的Markdown文件的标题等格式来进行切片
  • 元数据注入：每个切片都要附上上级标题链路层，防止信息漂移，如“[产品A说明书->硬件规格->电池寿命]”
  • 混合检索：Vector（稠密检索）抓主旨 + BM25（稀疏匹配）定位精确产品型号
  • Reranker重排序：提供更相关的信息、减少数据噪音（减少传递给LLM的无关信息）等

为什么要拆分多Agent

  • 单Agent + 工具调用在大部分场景都是最优解
    • 流程明确、任务简单：任务只需要调用1-5次工具，逻辑链条已知且线性执行
    • 延迟和成本更优
  • 在复杂任务下，单Agent硬瓶颈：
    • 上下文窗口饱和：所有工具的调用都集中在一个上下文窗口内
    • 注意力稀释：提示词庞大导致模型注意力被稀释
    • 角色冲突：部分任务要求保守合规、部分任务要求积极转化
    • 故障爆炸半径：一处出错，整条推理链断裂
  • 主流架构：Orchestrator-Worker架构（主控工人模式）
    • 主控Agent：负责理解用户需求，制订计划，把大任务拆解成小任务下发
    • 分解为若干子Agent：检索、分析、校验等
    • 主控Agent整合输出
  • 判断是否要拆：
    • 任务是否可以并行化
    • 是否存在专长领域冲突
    • 上下文是否过长
  • 常用的多Agent拓扑
    • 集中Supervisor：主Agent统一调度，子Agent互不通信，适用任务可清晰分析，子任务独立
    • 去中心化Swarm：Agent之间平等协商自由对话，适用探索性任务，需要涌现式合作
    • 层级式 Hierarchical：多层嵌套，逐层分解与汇总，适用于企业级复杂系统，可控性优先

大模型幻觉

关键认知

  • 从数学层面来看，幻觉难以被彻底消除，这是语言模型压缩世界知识时的必然代价。工程目标是多层防御、系统性降低。
  • 幻觉分类：
    • 事实性幻觉：编造不存在的内容
    • 忠实性幻觉：提供了资料，但是绕开资料使用自身训练记忆回答
    • 推理性幻觉：逻辑链条断裂导致结论错误

解决方案

  1. RAG检索增强生成：让模型有据可查，而不是凭自身训练记忆回答。主要解决事实性幻觉和忠实性幻觉。
    • 基础操作：
      • 混合检索：向量语义检索+BM25关键词检索结合互补盲区
      • 重排序：结果再经过Cross-Encoder模型精选一边
      • 语义分块：按照语义切分模型
    • 进阶：Agentic RAG
      • 智能体自行判断是否需要检索、评估检索结果质量是否需要再重新检索、多个智能体交叉验证结果
  2. Prompt工程：
    1. 边界约束：明确告知只用提供的资料回答问题，没有就说不知道
    2. 敢说不确定：给模型退路，让模型敢说“不确定”
    3. 思维链：让推理链条显示写出来，暴露自身错误
    4. 示例引导：给出“正确拒答”的范例
    5. 进阶：
      • Chain of Note：先写摘要笔记再作答，强迫模型“读资料”（在小模型上尤其需要）
      • Chain of Verification：拆解事实断言逐条核查，再出修订版（医疗、金融、法律等高风险场景使用）
  3. 输出约束：从生成到验证
    • 生成阶段：
      1. 调低温度：事实性任务调低温度（0.3以下），降低随机性
      2. 结构化输出：强制固定格式，杜绝格式幻觉
    • 生成输出->一致性检测->引用溯源->置信度打分->通过/重试
    • 提醒：过度对齐训练可能导致幻觉率升高，会让模型学会“取悦用户”而不是说真话

整体框架

  1. Prompt层：元认知约束，给模型画边界和退路
  2. RAG层：知识锚定，让回答有据可查
  3. 生成控制层：低随机性+结构化输出
  4. 后验证闭环层：一致性检测->引用溯源->置信度打分
  5. 可观测层：持续检测，使用工具持续追踪，把发现的幻觉问题反补回前面几层进行优化

面试回答

先回答从数学层面来看，幻觉难以被彻底消除，再按照整体框架五层分开讲，最后强调持续监控形成闭环。

JSON格式稳定性方法

三层次正确输出

  1. 语法正确：是否可以被解析
  2. 结构正确：字段、类型、枚举是否符合规则
  3. 业务正确：权限、金额、状态是否合理

三层防御

  1. 预防：清晰Prompt、Schema约束、上下文裁剪
    • 精细化Prompt：说清楚字段含义、数据类型、必填项、枚举值、控制规则与异常返回
    • 强约束机制：优先使用结构化输出、JSON Schema或工具参数Schema
    • 控制上下文
  2. 检测：JSON解析、结构校验、业务规则校验
    • 逐层验收：JSON解析->Schema校验->业务校验
  3. 兜底：有限重试、安全降级、日志与审查
    • 返回unknow、通用回复或可控的降级结果
    • 涉及复杂判断或高风险操作时，交给确定性流程处理
    • 记录与观测：记录模型、Prompt、Schema、错误类型、重试次数与最终结果

面试回答

  • 不仅依赖Prompt，而是靠预防、检测、兜底三层防御提高可靠性

Agent长期记忆

三层次记忆

  1. 短期会话记忆：最近N轮的完整对话，直接保留喂给模型。
  2. 结构化用户画像记忆：明确的事实信息，通过专门的处理程序，提取成结构化的标签，存入KV库或图谱。
  3. 长期情景记忆：无法结构化的历史对话切片向量化，进行语义检索。

生成逻辑

本质RAG：每一轮生成回复前，将系统提示词、用户画像标签、检索到的历史记忆片段、最近的短期对话，拼接成完整prompt再喂给大模型。

需要注意的设计细节：所有记忆的更新都放在后台异步线程完成，Summary Agent定期总结记忆+冲突清洗

面试回答

  • 分层存储：区分三层次记忆
  • 分类检索：事实类信息查结构化数据库、语境类内容用语义召回
  • 动态维护：记忆要更新和修正

智能体跑飞、死循环

智能体跑飞情景

  1. 死循环：重复调用同一工具，参数一致，无终止迹象
  2. 工具误调：查资料但是模型去调用了发邮件
  3. 目标漂移：长链路任务Agent遗忘最初目标
  4. 级联失败：一步出错后续全部基于错误结果推理
  5. 多Agent乒乓：多个Agent互相踢皮球
  6. 沉默失败：看似对了，但是结果错误，没有报错信号

如何发现

三层可观察性

  1. 全链路追踪：记录每一次思考、每一次工具调用、每一次记忆读写，形成完成轨迹图。

    落地方案：可追踪平台

  2. 异常检测规则：连续多轮相同工具调用触发告警，参数校验失败率超阈值自动告警，识别消息环路。

  3. 语义评估：使用一个小模型定期检查现在执行轨迹是否符合最初目标。

死循环检测

四个指标

  1. 重复计数：连续5-10轮工具名和参数哈希完全一致
  2. 进度量分析：使用小模型判断本轮对比上轮，任务状态有没有实质性推进
  3. Token消耗速率：Token持续消耗，但是没有任何实质性的结果
  4. 策略集合：记录全部已尝试的策略，重复尝试相同策略则判定为异常

兜底策略

五层纵深防御

  1. 硬限制：最大轮数（20轮）、最大耗时（120s）、Token预算
  2. 熔断器：某个工具连续失败自动熔断，模型异常自动切换
  3. 去重与进度追踪：每次调用生成指纹，防止重复执行同一操作
  4. 优雅降级：主路径无法跑通时降级为简化重试，输出已完成的部分结果
  5. 人机协同：置信度不足时挂起，高危操作必须人工确认

踩坑难点：

  • 如何判断合理重试和死循环：引入进度量分析
  • 熔断阈值怎么设：在真实流量场景下找到平衡点

Agent如何防御Prompt注入

  • 提示词加固无法彻底防御：
    • 模型根本上无法区分“指令”和“数据”，系统指令、工具返回、用户输入最终都会变成同一个Prompt。
    • 攻击者可以覆盖限制提示词。

纵深防御

  1. 输入侧：隔离与检测。

    • 结构隔离：不可信内容用结构化标签包裹。
    • 分类器扫描：在内容进入真正模型前使用独立的检测模型/引擎进行检测。
    • 拦截/降级：识别到风险后，恶意内容进行拒绝，可疑内容进行降权后放行。

  2. 模型侧：鲁棒与拒绝。

    • 对抗训练：微调阶段加入大量恶意注入样板，并标记为“拒绝执行”
    • 指令优先级：让模型理解 系统指令>工具数据>用户输入
    • 二次确认表达：敏感操作前，让模型先复述意图再执行

  3. 执行侧：执行与确认。

    • 最小权限原则：Agent只拥有完成任务的必要权限，能只读就不给写权限
    • 工具白名单：Agent能调用的工具都有白名单校验
    • 高风险人工确认：删除、支付、发送等操作必须要人工确认
    • 沙箱+读写分离：操作在隔离环境执行，读和写使用不同凭证

  4. 输出侧：过滤与追溯。

    • 输出内容过滤：对模型输出进行扫描，防止敏感数据、密钥、内部数据被带出去
    • 全链路日志：从输入、判决、推理到工具调用全部留痕
    • 异常可观察：监控异常高频调用、异常参数模式

面试回答

  • Prompt注入根因是模型根本上无法区分“指令”和“数据”，所以可以进行四层防御：输入隔离与检测、模型对抗训练、执行权限管控、输出过滤审计。

什么时候用GraphRAG

  1. 多维度查询，会把实体信息转化为图节点，类似于知识图谱，而传统rag最多搞语义模糊匹配
  2. 全局总结问题，会用社区检测算法，把知识图谱分成多各社区生成摘要，回答时使用map reduce方式汇总社区信息回答。
  3. 隐形关系理解，通过图结构捕捉到实体之间的隐形关系，在关联推荐分析具有价值
  4. 碎片化信息的串联导航，利用层次化结构，实现从宏观类别到微观实体的逐步缩小，检索效率高。
  5. 问题：成本高，token消耗和计算时间约是传统RAG十倍。索引阶段，实体识别，关系抽取，社区摘要都要调用llm。查询阶段需要检索更多的关联结点，计算量大
  6. 解决方式：混合路由，使用llm做意图识别，决定路径。简单查询用传统RAG，复杂问题用GraphRAG，结构化数据查询可以转SQL。

Zero-Shot零样本、Few-Shot少样本、CoT思维链

如何选择

  • Zero-Shot：适合任务表达清晰、模型已有通用能力、且追求响应效率的场景（简单任务）
    • 摘要、翻译、改写、提取
    • 通用回答、基础分类
    • 任务冷启动、暂无标注样本
    • 高并发、低延迟、成本敏感
  • Few-Shot：用少量示例完成上下文对齐（规则任务）
    • JSON、表格、固定字段等格式约束（格式锚定）
    • 客服、营销、法务等特定表达口径（风格对齐）
    • 领域术语、标签体系、判定标准（规则示例）
    • Zero-Shot输出一致性差
  • CoT：让复杂问题分布求解（复杂任务）
    • 复杂问题（条件多、规则多、步骤多）->拆解条件（识别已知、明确约束、规划步骤）->逐步推理（子问题求解、中间检查、汇总结论）->最终答案（逻辑更完整、过程可核验、结果更稳健）
    • 适用：数学、逻辑、多约束决策、代码分析、任务规划

递进式提示工程流程

  1. Zero-Shot基线：明确角色、任务、约束与输出格式
  2. Few-Shot对齐：补齐高质量、典型与边界示例
  3. CoT处理复杂性：拆解、验证，必要时多路径求解
  4. 评测与路由：质量、时延、成本，持续迭代优化
    • 离线测评：以真实任务集比较准确率、格式合规率、耗时与Token消耗
    • 按难度路由：简单请求走轻量链路、复杂任务再考虑CoT或增强策略
