21. 面试速答

Pi Agent 的 Compaction 本质上是一种 Incremental Context Checkpoint 增量式上下文检查点机制。

当上下文接近模型的 Context Window 上限时，系统会根据 Token Budget 找到合适的 Cut Point，将较老的历史压缩成 Structured Summary，同时通过 keepRecentTokens 保留最近一部分 Raw Messages。

在切分过程中，它会考虑 Turn Boundary 和 Tool Call / Tool Result 的结构关系，避免简单的 Token 截断；如果单个 Agent Turn 本身过长，则使用 Split-Turn Compaction。

Summary 主要保存 Goal 目标、Constraints & Preferences 约束与偏好、Progress 进展、Key Decisions 关键决策、Next Steps 下一步、Critical Context 关键上下文，以及 Read Files 已读取文件、Modified Files 已修改文件。

后续再次触发压缩时，会基于 Previous Summary 和新产生的历史进行增量更新。最终模型看到的是 System Prompt + Compaction Summary + Recent Raw Messages。

由于 Compaction 属于 Lossy Compression 有损压缩，所以权限、审批、Budget、Execution Status 等关键状态应该由代码和 State Store 确定性维护，而不能只依赖 LLM Summary。
